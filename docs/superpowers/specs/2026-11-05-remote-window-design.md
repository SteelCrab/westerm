# 원격 창: 서버의 westerm을 새 창에서 쓰기

- 날짜: 2026-11-05
- 상태: 초안 (승인 전)
- 브랜치: `feat/remote-window` (워크트리 `.claude/worktrees/feat-remote-window`, 기준 커밋 `bbf7539` = `origin/main`, v0.2.0)
- 앞선 설계: `2026-11-05-remote-quic-design.md` (v0.2.0의 원격 westerm 패인). 이 문서의 기능이 그 패인을 대신해요.

표시 규칙:

- **(사용자)**: 사용자가 정한 것. 대화에서 확인했어요.
- **(제 판단)**: 제가 정한 것. 사용자가 반대할 수 있어요.
- **(빌더)**: 구현하는 사람이 정해도 되는 것.

## 1. 의도와 이유

- 사용자는 주로 서버에서 일해요. 이 컴퓨터는 화면 역할을 해요. **(사용자)**
- 그래서 원하는 것은 "서버의 westerm을 새 창에서 그대로 쓰는 것"이에요. 그 창의 탭과 워크스페이스는 서버의 것이에요. **(사용자)**
- v0.2.0의 원격 westerm은 로컬 대시보드 안에 원격 셸 패인을 하나 열어요. 탭과 워크스페이스는 로컬에 있고, 셸만 서버에 있어요. 사용자는 이것이 "완전히 다른 것"이라고 했어요. **(사용자)**
- v0.2.0에서 만든 연결 부분은 그대로 다시 써요: SSH로 확인과 설치, `remote-setup`, QUIC gate, 인증서 고정, SSH 터널 대체, 서버 host 교체 질문.

## 2. 목표

- G1. 로컬 westerm에서 서버를 고르면 새 창이 열려요. macOS 앱에서는 새 앱 창, 브라우저에서는 새 브라우저 창이에요. **(사용자)**
- G2. 새 창은 평소 westerm과 똑같이 생겼어요. 창 제목에 서버 이름이 나와요. **(사용자)**
- G3. 그 창의 탭, 워크스페이스, 레이아웃은 서버에 저장돼요. **(사용자)**
- G4. 그 창의 셸, terminal-browser, terminal-code는 모두 서버에서 실행돼요. **(사용자)**
  - 테스트 서버에는 `terminal-browser`와 `tode`가 이미 `~/.local/bin`에 있어요 (2026-11-05 확인).
  - 서버 host는 모든 종류를 로그인 셸로 시작해요 (`spawn.rs`). 그런데 로그인 셸만으로는 `~/.zshrc`에서 더하는 `PATH`가 빠져요. 테스트 서버에서 `tode`를 찾지 못한 이유가 이것이에요.
  - 그래서 `remote-setup`이 사용자의 대화형 로그인 셸 `PATH`를 한 번 읽고, 그 `PATH`로 서버 host와 서버 대시보드를 시작해요. 읽지 못하면 지금 `PATH`에 `~/.local/bin`을 더해요. **(제 판단, 구현 중 확인)**
- G5. 창을 닫거나 네트워크가 끊겨도 서버의 작업은 계속돼요. 창을 다시 열면 같은 탭과 같은 셸이 보여요. **(사용자)**
- G6. 다른 컴퓨터에서 열어도 같은 탭과 워크스페이스가 보여요. **(사용자)**
  - 두 창이 같은 서버를 동시에 열면, 지금처럼 한 창만 세션을 가져요. 다른 창은 "다른 창에서 사용 중"을 보여 주고, 클릭하면 되찾아요. 이 규칙은 서버 host가 지켜요 (`host/registry.rs`). **(제 판단: 기존 규칙 그대로)**
- G7. 처음 열 때 SSH로 서버를 확인하고, 같은 버전의 westerm을 설치해요. **(사용자)**
- G8. 연결은 QUIC이에요. UDP가 막히면 SSH 터널을 써요. **(사용자)**
- G9. 네트워크가 돌아오면 창이 스스로 다시 연결돼요. 끊긴 동안에는 "재연결 중"을 보여 줘요. **(제 판단: v0.2.0 원격 패인의 규칙)**

## 3. 범위 밖 (non-goals)

- 한 창에 로컬 패인과 원격 패인을 섞는 것. 로컬 창과 원격 창은 서로 따로예요. 두 창 사이로 패인을 옮길 수 없어요. **(사용자)**
- v0.2.0의 원격 westerm 패인. 없애고 이 기능으로 바꿔요. **(사용자)**
- 원격 창 안에서 다른 서버의 원격 창을 여는 것 (중첩). **(제 판단)**
  - 원격 창의 SSH 패인과 원격 브라우저(`terminal-browser --ssh`)는 서버에서 실행되므로 그대로 돼요.
- 앱을 다시 열 때 원격 창을 자동으로 다시 여는 것. 팔레트나 활동 막대에서 다시 열어요. **(제 판단)**
- westerm 없이 브라우저만으로 서버에 접속하는 것. 원격 창은 항상 이 컴퓨터의 westerm을 거쳐요.
- 버전이 다른 두 컴퓨터가 같은 서버를 함께 쓰는 것. 높은 버전이 이기고, 낮은 버전의 컴퓨터는 먼저 업데이트해야 해요 (8.3). **(제 판단: v0.2.0 규칙)**
- v0.2.0과 같은 것: Linux가 아닌 서버, 비밀번호나 OTP SSH 인증, 서버 방화벽 자동 열기, systemd 서비스 등록.

## 4. 하면 안 되는 것 (anti-goals)

아래 중 하나라도 생기면, 기능이 동작해도 실패로 봐요.

- 서버에 다른 사용자가 연결할 수 있는 TCP 포트가 생기는 것. 서버 대시보드는 TCP로 듣지 않아요. 사용자만 열 수 있는 Unix 소켓으로만 들어요.
- gate가 등록되지 않은 클라이언트를 받는 것.
- 원격 명령 문자열에 사용자 입력이나 변하는 값이 들어가는 것. 원격 명령은 고정 문자열이고, 데이터는 stdin으로만 보내요 (v0.2.0 규칙).
- 연결이 끊겼는데 "연결됨"처럼 보이는 것.
- 창을 닫거나 네트워크가 끊겨서 서버의 셸이 끝나는 것.
- 끊긴 동안 닫은 패인의 셸이 서버에 영원히 남는 것 (v0.2.0 규칙, 8.4).
- 로컬 창의 동작이 바뀌는 것. 바뀌는 것은 진입점(8.4)과 원격 패인 제거뿐이에요.
- 다른 웹 사이트가 원격 창의 데이터(서버의 레이아웃, 호스트 목록, 셸)에 닿는 것 (8.7).
- 서버 사용자의 설정 파일(`.bashrc`, `.profile`, `PATH`)을 고치는 것.
- 체크섬을 확인하지 않은 실행 파일을 서버에 올리는 것.
- gate나 서버 대시보드 코드가 바뀔 때마다 셸이 재시작되는 것. 이 코드는 `HOST_SOURCES`에 넣지 않아요.

## 5. 제약

- 서버: Linux x86_64와 aarch64. 릴리스의 musl 정적 실행 파일 (v0.2.0과 같음).
- 로컬: macOS, Linux, Windows에서 빌드와 테스트가 통과해야 해요 (CI가 세 OS에서 돌아요).
- 로컬 대시보드는 계속 `127.0.0.1`에서만 들어요.
- UI 문구는 `src/i18n/messages.ts`에 네 언어(en, ko, ja, zh-CN)로 넣어요. 팔레트 `keywords`는 영어로 둬요.
- `shared/protocol.ts`와 `native/src/protocol.rs`는 함께 바꾸고, 양쪽에서 검증해요.
- `protocol.rs`는 `HOST_SOURCES`에 있어요. 원격 패인 종류(`remote`)를 빼면 host 빌드 id가 한 번 바뀌어요. 업데이트 후 로컬 셸이 한 번 "restored"로 다시 시작해요. 서버 host도 교체 대상이 되고, 셸이 있으면 v0.2.0 규칙대로 물어봐요. 이것은 받아들여요. **(제 판단)**
- v0.2.0은 이미 릴리스됐어요. 원격 패인 제거는 `CHANGELOG.md`의 "Removed"에 적어요.
- 문서: `docs/architecture.md`, `docs/sessions.md`, `docs/usage.md`, `CHANGELOG.md`를 함께 고쳐요. 레포 문서는 영어예요.

## 6. 구조

```
로컬 창   http://127.0.0.1:4317/                 ─┐
원격 창   http://127.0.0.1:4317/?remote=<대상>     ─┤ 같은 출처
                                                   ▼
로컬 대시보드 (127.0.0.1:4317)
  ├─ 화면 파일 (HTML, JS, CSS): 두 창 모두 여기서 받아요
  ├─ /api/…, /ws/session ─ Unix 소켓 ─ 로컬 host ─ 로컬 셸
  └─ /remote/<대상>/… ─ 원격 연결 관리자 (v0.2.0)
          ├─ QUIC (UDP) ─ 서버 gate ─┐
          └─ (대체) ssh -L 터널 ─────┤ Unix 소켓
                                     ▼
                         서버 대시보드 (원격 모드, TCP 없음)
                           ├─ workspace.json: 서버의 탭과 워크스페이스
                           ├─ 서버의 ~/.ssh/config 목록
                           └─ Unix 소켓 ─ 서버 host ─ 셸, terminal-browser, tode
```

- **서버 대시보드 (원격 모드, 새 실행 방식)**: 지금의 westerm 대시보드 코드예요. `remote-setup`이 시작해요. Unix 소켓으로만 들어요 (8.1).
- **서버 gate**: v0.2.0의 gate예요. 인증된 스트림을 host 대신 서버 대시보드의 소켓에 이어요 (8.2).
- **서버 host**: 그대로예요.
- **로컬 대시보드**: `/remote/<대상>/…` 요청을 그 대상의 연결로 넘겨요 (8.3).
- **원격 연결 관리자**: v0.2.0 코드를 다시 써요. 서버마다 연결 하나예요. 패인 대신 원격 창을 위해 연결을 유지해요.
- **화면 (SPA)**: 주소에 `?remote=<대상>`이 있으면 원격 창 모드로 돌아요 (8.4).

화면 파일을 로컬에서 주는 이유 **(제 판단)**:

- 플레이백에서는 "서버의 대시보드 화면을 QUIC으로 보여 준다"고 설명했어요. 사용자가 보는 결과는 같지만, 화면 파일(HTML, JS, CSS)만은 로컬에서 줘요.
- 끊긴 동안에도 창이 열리고 "재연결 중"을 보여 줄 수 있어요.
- 서버의 westerm은 항상 로컬과 같은 빌드예요 (G7). 그래서 화면 파일도 같아요.
- 화면 파일이 네트워크를 오가지 않아요.

같은 출처(`127.0.0.1:4317`)를 쓰는 이유 **(제 판단)**:

- 주소가 미리 정해져 있어요. 그래서 클릭하는 순간 바로 창을 열 수 있어요. 브라우저의 팝업 차단을 피해요.
- 지금의 출처 확인을 그대로 써요.
- 테마, 언어, 글꼴 크기 같은 설정(localStorage)을 로컬 창과 함께 써요.
- macOS 앱은 이미 이 출처를 창 안에서 열어요.

## 7. 원격 창을 여는 순서

1. 로컬 창에서 서버를 골라요. 팔레트의 "새 창에서 열기: <대상>" 또는 활동 막대의 원격 버튼 → 호스트 목록 (8.4).
2. 클릭 처리 안에서 바로 새 창을 열어요: 주소 `/?remote=<대상>`, 창 이름은 대상마다 하나. 같은 대상의 창이 이미 있으면 그 창을 앞으로 가져와요.
3. 새 창은 로컬 대시보드에서 화면 파일을 받고, 원격 창 모드로 시작해요. 연결 화면을 보여 줘요.
4. 화면은 로컬 대시보드에게 그 대상의 연결 상태를 받아요 (8.3). 로컬 대시보드는 v0.2.0과 같은 순서로 연결해요:
   1. 저장된 접속 정보가 있으면 SSH 없이 QUIC을 바로 시도해요.
   2. 안 되면 SSH로 서버를 확인해요 (CPU 종류, 설치된 westerm의 `--version`).
   3. westerm이 없거나, 로컬보다 오래됐거나, 같은 버전인데 빌드가 다르면 설치해요. 서버의 westerm이 더 새 버전이면 설치하지 않고 멈춰요 (8.3). v0.2.0의 `install_plan` 규칙 그대로예요. 그래서 연결된 서버 대시보드는 항상 로컬과 같은 빌드예요 (6절의 전제).
   4. SSH로 `remote-setup`을 실행해요. host, 서버 대시보드, gate를 준비하고 접속 정보를 받아요.
   5. QUIC으로 연결해요. 안 되면 SSH 터널을 써요.
5. 연결 화면에 단계를 보여 줘요: 서버 확인 중, westerm 설치 중, 연결 중. 서버 host 교체 질문도 여기서 보여 줘요 (v0.2.0 규칙: 셸이 있으면 묻고, "이전 host 계속 쓰기"를 고를 수 있어요).
6. 연결되면 `/remote/<대상>/api/workspace`로 서버의 레이아웃을 받아요. 저장된 레이아웃이 없으면 셸 하나로 시작해요. 로컬의 첫 실행과 같아요.
7. 패인은 `/remote/<대상>/ws/session`으로 서버 host의 세션에 붙어요. 그다음은 로컬 패인과 같아요.

## 8. 세부 설계

### 8.1 서버 대시보드 (원격 모드) **(제 판단)**

- 시작: `remote-setup`이 host, 서버 대시보드, gate를 차례로 확인해요.
  - 서버 대시보드는 셸을 붙잡지 않아요. 그래서 빌드가 다르면 gate처럼 바로 교체해요.
  - host 교체 규칙은 v0.2.0 그대로예요.
- 서버 대시보드는 돌고 있는 host를 교체하지 않아요.
  - 로컬 대시보드의 `HostClient::ensure`는 빌드가 다른 host를 조용히 교체해요. 원격 모드에서는 이 동작을 쓰지 않아요.
  - host가 없을 때 시작하는 것만 해요. 교체는 `remote-setup`이 질문 규칙에 따라 해요.
- 듣는 곳: 상태 폴더 안의 Unix 소켓 하나 (권한 0600). TCP 포트는 열지 않아요.
- 답하는 경로는 원격 창에 필요한 것만이에요. 나머지는 404예요.
  - `GET`, `PUT /api/workspace`: 서버의 탭과 워크스페이스.
  - `GET /api/ssh-hosts`: 서버의 `~/.ssh/config` 목록. 원격 창의 SSH 패인은 서버에서 실행되기 때문이에요.
  - `GET /ws/session` (WebSocket): 서버 host의 세션.
- 출처 확인을 하지 않아요. 소켓은 사용자만 열 수 있고, 요청은 gate나 SSH 터널로만 와요. 출처 확인은 로컬 대시보드가 해요 (8.3).
- 업데이트 확인을 하지 않아요. 서버의 westerm은 로컬 버전을 따라가요 (G7).
- 상태 폴더는 기본 위치(`~/.local/state/westerm`) 그대로예요.
  - 서버에서 westerm을 직접 쓰면, 서버에서 연 창과 원격 창이 같은 host와 같은 `workspace.json`을 써요. 그래서 같은 탭이 보여요.
  - 창끼리는 G6의 규칙(한 창만 세션을 가짐)을 따라요.
- `remote-setup`의 JSON에 서버 대시보드 소켓 경로를 더해요. SSH 터널이 이 경로를 써요. host 소켓 경로는 더 쓰지 않아요.
- `westerm stop`은 host, gate와 함께 서버 대시보드도 멈춰요.

### 8.2 gate **(제 판단)**

- 인증, 포트, 주소 검증은 v0.2.0 그대로예요: TLS 1.3 상호 인증, 지문 고정, `authorized_clients`, UDP 4317–4326, QUIC Retry.
- 받은 스트림마다 서버 대시보드 소켓에 연결하고, 양쪽 바이트를 그대로 이어요.
- 첫 요청 줄 검사(v0.2.0의 `/session` 업그레이드만 허용)는 없애요. 허용할 경로는 서버 대시보드가 정해요 (8.1). 서버 대시보드의 소켓에는 원격 창에 필요한 경로만 있어서, 다른 경로로 갈 수 없어요.
- gate에서 서버 host 소켓으로 가는 길은 없애요.

### 8.3 로컬 대시보드 **(제 판단)**

- 새 경로: `/remote/<대상>/api/workspace`, `/remote/<대상>/api/ssh-hosts`, `/remote/<대상>/ws/session`.
  - 그 대상의 연결로 넘겨서, 서버 대시보드의 같은 경로로 보내요.
  - 대상은 `normalize_ssh_target`으로 검증해요. 틀리면 400이에요.
- 출처 확인: 지금의 규칙 그대로예요. `PUT`과 WebSocket은 대시보드 자신의 출처만 받아요.
- Host 헤더 확인: 원격 경로는 `Host`가 `127.0.0.1:<포트>` 또는 `localhost:<포트>`일 때만 받아요. DNS rebinding으로 다른 사이트가 서버의 레이아웃이나 호스트 목록을 읽지 못하게 해요. 로컬 경로에도 같이 적용할지는 빌더가 정해요 (Vite 개발 서버를 확인해야 해요). **(빌더: 로컬 경로 적용 여부)**
- 연결 상태 경로 (로컬에서 답해요): 원격 창이 연결 단계와 상태를 받는 곳이에요. v0.2.0의 단계(`RemoteStage`)와 실패 종류(`RemoteFailure`)를 다시 써요. 지금은 이 정보가 세션 WebSocket 안으로 와요. 이제는 창 하나에 상태 흐름 하나예요. **(빌더: 경로 이름, WebSocket 또는 SSE)**
- 서버 host 교체 질문의 답은 v0.2.0의 `/api/remote/decision`을 그대로 써요.
- 연결 유지:
  - 원격 창이 하나라도 상태 흐름을 열고 있으면 연결을 유지해요.
  - 마지막 창이 닫히면 잠시 뒤 연결을 닫아요. 서버의 세션은 계속 돌아요. **(빌더: 기다리는 시간)**
- 다시 연결: 끊기면 7번의 순서로 다시 붙어요.
  - 일시 실패(서버에 닿지 않음, 전송 오류)는 원격 창이 열려 있는 동안 계속 다시 시도해요. 간격은 점점 늘려요.
  - SSH 로그인은 자주 하지 않아요. 저장된 접속 정보로 QUIC을 다시 시도하는 것은 자주 해도 돼요. SSH 확인과 `remote-setup`은 간격을 길게 둬요. 로그인 실패를 막는 서버 도구(fail2ban 같은)를 건드리지 않기 위해서예요. **(빌더: 간격 값)**
  - 영구 실패는 자동 재시도를 멈춰요: SSH 인증 실패, `known_hosts`에 없음, 지원하지 않는 서버, 서버가 더 새 버전, 맞지 않는 host. v0.2.0의 `is_permanent()` 규칙 그대로예요. 창은 이유와 해결 방법, 그리고 "다시 시도" 버튼을 보여 줘요.
  - 다시 연결하는 중에 설치나 gate, 서버 대시보드 교체가 필요하면 스스로 해요. 로컬 westerm을 업데이트한 뒤가 대표적인 경우예요. 서버 host 교체는 셸이 있으면 항상 먼저 물어요.
- 버전이 다른 두 컴퓨터 **(제 판단: v0.2.0 규칙)**:
  - 서버의 westerm은 다운그레이드하지 않아요. 그래서 높은 버전이 이겨요.
  - 낮은 버전의 컴퓨터는 영구 실패를 보여 줘요: "서버의 westerm이 더 새 버전이에요. 이 컴퓨터의 westerm을 업데이트하세요."
  - 버전끼리 맞추는 호환 번호는 만들지 않아요. 화면은 서버 대시보드가 같은 빌드라고 가정해도 돼요.
- 연결이 없을 때 원격 경로로 온 요청은 바로 실패해도 돼요 (예: 503). 화면이 상태 흐름을 보고 다시 시도해요. **(빌더)**

### 8.4 화면 (SPA) **(제 판단)**

원격 창 모드 (`?remote=<대상>`):

- `/api/workspace`, `/api/ssh-hosts`, `/ws/session` 앞에 `/remote/<대상>`을 붙여요.
- `/api/terminal-config`는 로컬 그대로예요. 그래서 글꼴은 이 컴퓨터의 Ghostty 설정을 따라요.
- 제목은 `westerm — <대상>`이에요. macOS 앱은 원격 창의 페이지 제목을 창 제목으로 써요.
- 어느 서버에 어떻게 연결됐는지 보여 줘요. 예: 머리말에 서버 이름과 `QUIC` 또는 `SSH 터널`. **(빌더: 모양)**
- 처음 연결 동안에는 창 전체에 연결 화면을 보여 줘요. 단계와 오류를 보여 줘요. 오류 문구는 v0.2.0의 "원인 + 해결 방법" 문구를 다시 써요.
- 끊기면 "재연결 중" 띠를 보여 줘요. 패인은 횟수 제한 없이 다시 붙어요. v0.2.0 원격 패인의 규칙을 원격 창의 모든 패인에 적용해요.
- 영구 실패(8.3)면 띠 대신 이유와 "다시 시도" 버튼을 보여 줘요.
- 끊긴 동안 닫은 패인, 탭, 워크스페이스는 v0.2.0 방식 그대로 처리해요.
  - 화면이 로컬 대시보드에 세션 id를 알려요 (`/api/remote/close`).
  - 로컬 대시보드가 기억했다가 (`remote/pending-close.json`), 다시 연결되면 서버에서 끝내요 (`deliver_closes`).
  - 이 기록은 닫은 컴퓨터에만 있어요. 그래도 셸은 그 컴퓨터가 다시 연결될 때 끝나요.
- 끊긴 동안에는 레이아웃을 저장하지 않고 "바뀜"으로 표시해요. 다시 연결되면 먼저 서버의 레이아웃을 읽어요. **(제 판단, 최종 리뷰 뒤)**
  - 이 창이 마지막으로 맞춘 레이아웃과 같으면, 바뀐 것이 있을 때만 저장해요.
  - 다르면 다른 컴퓨터가 바꾼 것이에요. 서버의 레이아웃을 따르고, 저장하지 않아요.
  - 알려진 한계: 다시 연결된 창의 패인은 스스로 세션에 다시 붙어서, 다른 컴퓨터에서 쓰던 창의 세션을 가져갈 수 있어요. 데이터는 잃지 않아요. 그 창을 클릭하면 되찾아요.
- 로컬 westerm이 업데이트되면 원격 창도 새로 고쳐요. 그러면 화면 파일이 새 빌드가 되고, 다시 연결할 때 서버도 새 빌드로 바뀌어요.
- 업데이트 버튼은 보여 주지 않아요. 서버의 westerm은 로컬 버전을 따라가요.
- "새 창에서 열기"는 보여 주지 않아요 (중첩 안 함).
- 팔레트에 "이 서버의 westerm host 업데이트"를 둬요. v0.2.0의 "원격 host 업데이트: <대상>"을 원격 창 안으로 옮긴 거예요.

로컬 창:

- 팔레트: SSH 호스트마다 있던 `westerm <대상>`을 "새 창에서 열기: <대상>"으로 바꿔요. `user@host` 입력도 그대로 돼요.
- 활동 막대: 원격 westerm 버튼은 호스트 목록을 보여 주고, 고르면 원격 창을 열어요. **(빌더: 문구, 아이콘)**
- 원격 패인을 없애요: `remote` 세션 종류, 패인 단계 표시, 패인 안의 결정 버튼, 원격 relay. 서버 host 교체 질문은 원격 창의 연결 화면이나 띠로 옮겨요. `/api/remote/close`는 원격 창이 계속 써요.
- 저장된 레이아웃의 `remote` 세션 (v0.2.0): 읽을 때 빼요. 비게 된 탭도 빼요. 그 셸은 서버 host에 남지만, 서버에서 `westerm stop`을 하면 끝나요. 이 내용은 `CHANGELOG.md`에 적어요.

### 8.5 macOS 앱 **(제 판단)**

- 창을 여러 개 열 수 있게 해요. 원격 창은 새 `NSWindow`와 `WKWebView`예요.
- 페이지가 새 창을 열면(`createWebViewWith`), 주소가 대시보드 출처이고 `remote=`가 있을 때만 앱 창을 만들어요. 받은 configuration으로 만든 `WKWebView`를 돌려줘요. 다른 주소는 지금처럼 기본 브라우저로 열어요.
- 같은 대상의 창이 이미 있으면 그 창을 앞으로 가져와요.
- 원격 창의 제목은 페이지 제목을 따라가요.
- 원격 창을 닫아도 서버의 세션은 그대로예요. 마지막 창을 닫으면 지금처럼 앱이 끝나요.
- 메인 창을 닫고 원격 창만 남았을 때 메인 창을 다시 여는 방법(예: Dock 클릭). **(빌더)**
- 창 크기와 위치는 대상마다 기억해요. **(빌더)**
- LAN 서버에 QUIC을 쓰려면 Local Network 권한이 필요해요 (v0.2.0과 같음).

### 8.6 저장 파일

로컬 상태 폴더: v0.2.0 그대로예요 (`remote/client.*`, `remote/hosts/<대상>.json`, `remote/pending-close.json`, `remote/bin/…`, `remote/t-*.sock`).

서버 상태 폴더 (`~/.local/state/westerm`):

| 경로 | 내용 |
|---|---|
| `workspace.json` | 서버의 탭과 워크스페이스. 지금의 형식 그대로예요. |
| 서버 대시보드 소켓, 잠금, 기록, 로그 | 새 파일이에요. gate의 `gate.lock`, `gate.json`, `gate.log`와 같은 방식이에요. **(빌더: 이름)** |
| `remote/gate.*`, `remote/authorized_clients`, `gate.*` | v0.2.0 그대로예요. |

### 8.7 보안

- 서버에 새로 열리는 포트는 없어요. gate의 UDP 포트는 v0.2.0과 같아요. 서버 대시보드는 Unix 소켓(0600)만 써요.
- 서버 대시보드에 닿는 길은 둘뿐이에요: 인증된 gate, 그리고 SSH 터널. 둘 다 사용자 본인의 인증이 필요해요.
- 원격 경로는 출처와 Host 헤더를 모두 확인해요 (8.3). 다른 사이트의 페이지가 원격 셸을 열거나, 서버 레이아웃을 읽거나 고치지 못해요.
- 남는 위험(문서화): 로컬 `127.0.0.1:4317`은 지금처럼 이 컴퓨터의 다른 프로그램이 접근할 수 있어요. 이 프로그램은 원격 창의 경로로 서버의 셸도 열 수 있어요. v0.2.0 원격 패인과 같은 위험이에요. "Known gap"을 고쳐 적어요.
- `docs/architecture.md`의 Security 절에 위 내용을 적어요.

## 9. 테스트

- 단위 테스트 (Rust):
  - 서버 대시보드 원격 모드: 세 경로만 답하고, 나머지는 404.
  - 로컬 원격 경로: 잘못된 대상은 400. 다른 출처의 `PUT`과 WebSocket은 거부. 다른 `Host`는 거부.
  - `remote-setup` JSON의 새 필드 읽기와 잘못된 입력 거부.
- 통합 테스트 (`native/tests/`, 실제 실행 파일, v0.2.0의 가짜 `ssh` 재사용):
  - 임시 상태 폴더로 서버 쪽(host, 서버 대시보드, gate)을 띄워요. 로컬 대시보드로 `PUT /remote/<대상>/api/workspace`를 하면 서버 쪽 `workspace.json`에 저장되고, `GET`으로 같은 내용이 돌아와요.
  - `/remote/<대상>/ws/session`으로 셸에 붙고 출력을 확인해요. 연결을 끊고 다시 붙으면 같은 셸이에요.
  - `WESTERM_REMOTE_TRANSPORT=tunnel`에서도 같은 결과예요.
  - 등록되지 않은 클라이언트는 거부돼요 (v0.2.0 테스트 유지).
  - 서버가 더 새 버전이면 설치하지 않고 영구 실패를 알려요 (v0.2.0 테스트 유지).
  - 끊긴 동안 닫은 세션은 다시 연결되면 서버에서 끝나요 (v0.2.0 테스트를 원격 창 경로로 옮겨요).
  - 서버 대시보드는 빌드가 다른 host를 교체하지 않아요.
  - 서버 대시보드는 TCP 포트를 열지 않아요.
  - Windows CI에서는 서버 쪽 테스트를 건너뛰어요.
- UI 테스트 (`node:test`):
  - `?remote=prod`이면 경로 앞에 `/remote/prod`가 붙어요. 로컬 창은 그대로예요.
  - 원격 창 모드의 패인은 재연결을 멈추지 않아요. 로컬 셸은 지금처럼 멈춰요.
  - 영구 실패면 재시도를 멈추고 "다시 시도" 버튼을 보여 줘요.
  - 다시 연결되면 마지막 레이아웃을 한 번 저장해요.
  - 원격 창 모드에는 업데이트 버튼과 "새 창에서 열기"가 없어요.
  - 팔레트의 "새 창에서 열기: prod"는 `/?remote=prod` 창을 열어요.
  - 저장 파일의 `remote` 세션은 빼고 읽어요. 비게 된 탭도 빼요.
- 수동 종단 테스트: 테스트 서버 `pista@msi-linux-private-pista` **(사용자)**
  - macOS 앱과 브라우저에서 원격 창을 열고, 제목을 확인해요.
  - 탭과 워크스페이스를 만들고, 창을 닫았다 다시 열어요. 같은 탭과 셸이 보여야 해요.
  - 서버에서 terminal-browser와 tode를 실행해요.
  - Wi‑Fi를 껐다 켜요. 창이 스스로 다시 연결되고, 같은 셸이 보여야 해요.
  - 다른 클라이언트(다른 로컬 상태 폴더)로 열어도 같은 탭이 보여야 해요 (G6).
  - UDP를 막으면 SSH 터널로 바뀌어요.

## 11. 빌더에게 맡기는 것

- 경로, 옵션, 파일, 메시지, 함수 이름. 서버 대시보드를 시작하는 방법 (예: `serve`의 숨은 옵션 또는 새 명령).
- 연결 상태 흐름의 모양 (WebSocket 또는 SSE)과 메시지 모양.
- 마지막 원격 창이 닫힌 뒤 연결을 닫기까지 기다리는 시간.
- 다시 연결할 때의 간격 값 (QUIC 재시도, SSH 확인).
- 연결 화면, 연결 표시, "재연결 중" 띠의 모양과 문구, 아이콘.
- 브라우저에서 새 창을 여는 `window.open` 옵션.
- macOS 앱의 창 위치 기억 방법과 메인 창을 다시 여는 방법.
- 로컬 경로에도 Host 헤더 확인을 적용할지 여부.
- 연결이 없을 때 원격 경로가 돌려줄 응답.

## 12. 의존 관계와 위험

- 다른 작업: `feat/workspace-switcher` 워크트리가 진행 중이에요 (워크스페이스 UI). `App.tsx`, `workspace.ts`, 사이드바에서 충돌할 수 있어요. 그 작업이 먼저 `main`에 들어가면 이 브랜치를 그 위로 옮겨요. **(제 판단)**
- v0.2.0 사용자: 원격 패인이 사라져요. 저장된 원격 패인은 레이아웃에서 빠져요 (8.4).
- 브라우저 팝업 차단: 새 창은 클릭 처리 안에서 바로 열어야 해요. 주소가 미리 정해져 있어서 가능해요.
- `WKWebView`: `createWebViewWith`에서 받은 configuration으로 만든 web view를 돌려주지 않으면 창이 비어요.
- macOS의 Local Network 권한이 없으면 LAN 서버에 QUIC이 안 되고, SSH 터널을 써요 (v0.2.0에서 확인한 내용).
- QUIC은 UDP가 막힌 곳에서 안 돼요. SSH 터널이 이 위험을 줄여요.
